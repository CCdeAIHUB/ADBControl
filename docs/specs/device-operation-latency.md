# 设备操作延迟隔离

## 目标

桌面端对一台在线设备执行触控、解锁、终端、文件、软件包或其他 ADB 操作时，不得等待其他已保存设备的发现、重连或超时。

## 根因证据

- 目标设备的 adb get-state 实测低于 100 ms，普通 shell 命令约 100 ms，唤醒与上滑命令均在 1 秒内返回；
- 另一台离线无线设备的单次 adb connect 实测超过 20 秒；
- 原实现把后台所有设备重连和前台 EnsureDeviceOnlineAsync 放在同一全局锁内，并在每次前台操作前再次执行全量刷新；
- 多次操作会把多轮全量刷新排队，形成约 1 到 2 分钟的反馈延迟。

## 行为规则

1. IsConnected=true 的目标设备直接进入操作，不执行前置全量刷新。
2. 目标状态未知时，只读取目标可用性快照；不得等待其他设备的连接锁。
3. 连接互斥以设备对象为边界；一台设备的连接超时不得阻塞另一台设备。
4. 已绑定稳定 mDNS ID 的设备若当前没有匹配服务，后台不得尝试保存的临时端口。
5. 用户显式点击连接时，仍允许尝试保存端点，以支持主动诊断和旧式 TCP/IP ADB。
6. 权限拒绝、命令语法、软件包不存在等操作错误不得把 transport 状态改为离线。
7. 只有设备 offline、unauthorized、not found、transport/connection 中断或 ADB 超时可以把设备标记为离线。

## 可观测性

连接诊断写入 %LOCALAPPDATA%\ADBControl\logs\device-connection.log，使用 JSON Lines，包含 traceId、阶段、总耗时、队列等待耗时、结果和稳定错误码。日志只保存设备 ID 的 SHA-256 摘要，不保存原始序列号或 IP。

## TDD 场景

- 场景：设备 A 的重连挂起时，已知在线的设备 B 必须在 250 ms 内完成前台在线判定。
- 场景：稳定 mDNS 服务缺失时，后台刷新不能调用过期保存端点；显式连接仍应调用。
- 场景：权限和业务命令失败不能判定设备离线；error: device offline 必须判定离线。
- 场景：连接日志必须包含 trace 与耗时，并且不能包含原始设备 ID。
